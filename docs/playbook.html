Prompts I type often

Catch up.

Brief me on the [project]. Read STATUS.md and the last few commits.
What's done, what's open, what's blocked, and on whom?

Explore, don't confirm.

Use discovery mode. Keep exploring until you find something
I didn't expect, or can show there's nothing there.
Before each analysis, write what an artifact would look like.

Try to kill it.

Here is the result. List the three explanations most likely to make it
an artifact, run the checks, and report which ones it survives.
Check that every control produced real numbers.

After a talk.

After my talk people asked: [questions].
For each one: can we answer it with data we already have?
If yes, do it. If no, say what it would take.

Clean-room reproduction.

In a new directory, rebuild these results from the Methods text only.
Don't use existing intermediate files. Keep going until it runs end to end,
then list every place the text wasn't enough.

Report to my advisor.

Summarize what changed this week for my advisor. Lead with results and
plots, plain language, one line per finding, with where the file is.
Flag anything that reverses something I told her before.

Literature round.

Read [group]'s recent papers on [topic]. What methods do they treat as
standard? Which could I apply to my data, and what would it cost?
Quote the paper for every claim; mark anything you couldn't verify.

A rules file (CLAUDE.md) skeleton

# Project: [name]

## Where things are
- Raw data: [path] (read-only, never modify)
- Outputs: [path]
- Status: STATUS.md, read first

## How to run things
- Heavy work goes in batch jobs, not the login node
- Load software as: [exact commands]
- Check a job is actually running after submitting it

## Never
- Delete or overwrite raw data
- Report a number without the file it came from
- Commit in someone else's working copy

## Figures
- See FIGURE_RULES.md

## Mistakes that happened (one line each, newest first)
- [date] Control returned empty and was reported as a pass. Assert controls ran.

Plotting rules

I keep these in one file the agent reads before any figure. The short version:

  1. One figure, one panel. Compose multi-panel figures later in slides or LaTeX.
  2. Two sizes. Slides: big text (axis titles around 30 pt). Manuscript: column width, smaller text.
  3. Every plot shows its n, and writes a small stats table from the same data it plotted.
  4. Plot type follows the data. Bounded values get box plus dots, not violins. Bars start at zero. Log scale only when values span two or more orders of magnitude, and never for bars.
  5. Colour is a fixed system. One palette file. Each thing keeps its colour for the whole project. Colourblind-safe.
  6. No invented cutoffs. Every threshold is justified, cited, or shown as a range.
  7. Don't hide structure by averaging. Show replicates, haplotypes, and batches separately.
  8. No titles. Context goes in the filename and caption.
  9. Look at the rendered image before calling it done: nothing clipped, nothing overlapping.

Workflow: prototype to a link

For anything visual (an explainer, a game, a figure gallery, a data browser):

flowchart TB
  A["Private GitHub repo"] --> B["Plain HTML in docs/"]
  B --> C["Turn on GitHub Pages"]
  C --> D["Push first rough version"]
  D --> E["Agent opens the live URL
in a headless browser"]
  E --> F["Send the link"]
  • Do it on the first working version, not at the end. A URL you can open on a phone gets feedback; a branch doesn't.
  • The repo can be private, but the site is public. Only put cleared material in docs/.
  • No build step unless there's a real reason. Files that open by double-clicking.
  • Check the live page, not the local file.

Workflow: a data atlas from analysis repos

One static site that lets people browse every gene (or sample, or site) with all the layers from different analyses in one place.

flowchart TB
  A["Analysis repo A"] --> S["Build scripts
pin each source file + checksum"]
  B["Analysis repo B"] --> S
  S --> D["Small JSON shards
committed in the site repo"]
  D --> W["Static site on Pages
search, tables, per-gene page"]
  L["Each repo's corrections log"] -.->|read before rebuild| S
  • The committed data is the artifact. The site never computes; it just reads shards.
  • Pin every source. Version and checksum each input, and fail the build if it changes unexpectedly.
  • Watch upstream corrections. The blind spot: every check compared the site to itself, so when an upstream analysis was corrected, the site kept serving the old version for days with every check passing. Now the build reads each source's corrections log first.
  • Tag a frozen version when you cite it anywhere.

Workflow: running analysis for another group

From running an amplicon sequencing pipeline as a service for several labs:

  • One shared pipeline, one repo per client project. Each project pulls in the pipeline as a submodule and holds only its own config, metadata and results.
  • Check the design before the statistics. Ask the agent to generate a short "what can this design estimate?" note from the metadata. It caught a case where one factor completely determined another, so a three-factor plot really showed two.
  • Don't invent comparisons. If there's no metadata, deliver composition and per-sample summaries, and say why there are no group tests.
  • Pre-commit the decision rule when comparing two methods, then report where they disagree, not just which won.
  • Read the draft against the data. A draft once described more samples and more controls than were actually sequenced. Finding that before submission is the service.
  • Large files aren't repo files. Commit a manifest and checksum; keep the file on storage.

Workflow: several agents at once

  • One git worktree per session. Never two sessions in one working copy.
  • Chain batch jobs with dependencies so no agent has to wait and poll.
  • Every few days, ask one session to review what the others did: "Did anything go wrong? What needs a human?"
