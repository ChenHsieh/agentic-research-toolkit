How I actually use it

I'm a PhD student in plant genomics. Since September 2026 I've run about 75 Claude Code sessions on our university cluster, plus a handful on my laptop, mostly for reviewing and planning. This page is what that looks like in practice, written for labmates who keep asking.

The setup

  • Claude Code, in a terminal, on the cluster. I open a compute node inside tmux, start claude in the project folder, and leave it running. The agent reads files, writes scripts, submits Slurm jobs, checks on them, and commits to git.
  • My phone. Remote Control lets me read and answer a running session from my phone. Most of my prompts are short replies between other things.
  • Several sessions at once. Usually one per project. They are not aware of each other unless I tell them, which matters (see below).
  • Codex, occasionally. Mostly as a second pair of eyes on something Claude set up.

You do not need a cluster to start. The same tool runs on a laptop in any folder.

What I ask it to do

Roughly in order of how often:

  • Status and catch-up. "Brief me on the 16S project." "Where are we on the duplication work, and what's still open?"
  • Run an analysis end to end. "Run phylostratr and one other tool on the same genes so we can compare to genEra." It writes the scripts, sizes the jobs, submits them, and reports back.
  • Follow up on feedback. "After my talk people asked X and Y. Work out what we can answer with data we already have."
  • Figures. "Redo these plots with log10 axes and the sample size on every panel." I keep my figure rules in a file so I don't repeat them.
  • Literature. "Read this group's last few papers on duplication and epigenetics. What are their standard methods, and which apply to my data?"
  • Reproducibility checks. "In a fresh folder, rebuild these results from the Methods text only, without the existing intermediate files. Tell me where the text is not enough."
  • Second opinion. "Read this public page and flag every claim the data doesn't support." "Here is a proposed set of criteria. What's missing or wrong?"
  • Housekeeping. Organize a messy directory into a GitHub repo, clean up branches, move data to the right storage.
  • Reports for people. "Summarize this week's results for my advisor in Slack, with the plots, so she knows what to discuss tomorrow."
  • Side projects. Small web games and explainers, published as GitHub Pages sites.

In those sessions the agent ran about 13,000 actions. Most were ordinary: reading files, running Python, editing scripts, checking the job queue, using git. It is less "AI" than it sounds. It's a fast, tireless person at a terminal who needs supervising.

What makes it work

  1. A rules file per project. Claude Code reads a CLAUDE.md file at startup. Mine says where data lives, which partitions to use, how to load software, what never to delete, and how I want figures to look. Every time the agent makes a mistake I'd rather not see again, one line goes in. Template here.
  2. Hand-off notes in files, not in chat. Conversations get long and older parts get summarized away. I ask the agent to keep a short status file (what's done, what's open, where outputs are) and to start new sessions by reading it.
  3. Results go into git. Scripts, small result tables, and figures get committed with a plain message. If a number only exists in a chat window, it doesn't exist.
  4. Ask it to break its own result. "What would this look like if it were an artifact? Run that check." This has caught more errors than anything else I do.
  5. One working copy per session. When two sessions edit the same git checkout, one eventually commits the other's half-finished work. Each session now gets its own git worktree.
  6. Let the scheduler wait, not the agent. Chain jobs with Slurm dependencies instead of having the agent sit and poll. It's cheaper and nothing gets forgotten.

What went wrong

All of these happened to me, more than once:

  • A control that never ran. A comparison came back empty, and the summary reported it as "passed". Now I check that every control produced real numbers.
  • A plausible number with no source. Always ask where a number came from, and open the file.
  • The wrong unit of analysis. A result looked strong when every gene was counted separately and disappeared when related genes were grouped. The agent will not catch this by default. You have to ask.
  • Confident wrong facts about the environment. Software versions, paths, which partitions I can use. It guesses. The rules file fixes this over time.
  • Sessions stepping on each other. See the worktree rule above.
  • Lost work. A job crashed while printing its summary, before the results were saved. Save first, then print.

None of these are exotic. They're the mistakes a new rotation student makes, at ten times the speed.

If you're starting this week

  1. Install Claude Code on your laptop and log in with the lab account. (Setup steps are in the official docs.)
  2. Pick one small, real task you already know the answer to. For example: "Read this folder and tell me what each script does and what order to run them in."
  3. Leave permission prompts on. Read what it wants to run before you approve it.
  4. After the first session, write a CLAUDE.md with five lines about your project. Add a line every time something goes wrong.
  5. Only then try something you don't know the answer to, and check it as if a student had done it.

Not ready for a terminal? A plain chat is still useful. Start at Level 1.
