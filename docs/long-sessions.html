Models and long sessions

Which model to use, and how to let a session run for hours without losing track of what it did.

Picking a model

Model names and prices change every few months, so here is the rule rather than a ranking.

flowchart TB
  Q{"Is the hard part judgement
or volume?"} -->|judgement| S["Strongest model, more thinking
planning, design, review, debugging"]
  Q -->|volume| F["Faster, cheaper model
bulk edits, reformatting, simple scripts"]
  S --> R["Review the volume work
with the strong model"]
  F --> R
  • Default to the strongest model you have for anything where being wrong is expensive: designing an analysis, reading results, deciding what's next, reviewing another session's work. The cost difference is small next to a wrong result you act on.
  • Turn thinking up for hard problems and down for chores. A rename doesn't need deep reasoning; a confusing result does.
  • Use cheaper models for volume, such as subagents fanning out over many files, then have the strong model check the output.
  • Check which model actually answered. Tools can fall back to another model when one is busy. If a session suddenly gets sloppier, look.
  • Judge models on your own tasks. Give two models the same real task you already know the answer to. That beats any leaderboard.
  • A second tool as a second opinion. I sometimes ask a different agent (Codex) to review what Claude set up. Disagreements are where the bugs are.

Long sessions: what goes wrong

  • It forgets. When a conversation gets long, older parts are summarized. Details, numbers and decisions from three hours ago can quietly drop out.
  • It drifts. After many steps it can solve a slightly different problem than the one you asked about.
  • "Running" isn't "working". A background helper can sit stuck for hours while reporting that it's busy.
  • The summary is a story. The end-of-session report is what the agent believes it did, not necessarily what happened.

Long sessions: how to harness them

flowchart TB
  B["Brief in a file
goal, inputs, done means"] --> W["Work in steps
task list kept up to date"]
  W --> C["Checkpoint each step
commit + update STATUS.md"]
  C --> W
  C --> E["End: a fresh session
reviews the files, not the chat"]
  1. Put the brief in a file. Goal, inputs, what "done" means, known traps. When memory gets summarized, the file is still there to re-read.
  2. Ask for a task list and have it updated as steps finish. It's the session's spine and your progress bar.
  3. Checkpoint to disk. After each real step: commit, and update a short STATUS.md. Save results before printing summaries.
  4. Let jobs run without an agent watching. Chain batch jobs with dependencies, or use one watcher that wakes the session when the job ends. Don't pay for an agent to poll.
  5. Make long jobs resumable. Write results as you go and skip finished items on restart, so a crash costs minutes, not the run.
  6. Check on helpers by their output. Look at whether files are actually changing, not at the status label.
  7. Review with fresh eyes. At the end, start a new session, point it at the commits and output files, and ask: "What did this actually do? What's wrong or unsupported?"
  8. Trust artifacts, not narration. A number counts when you can open the file it came from.

The good part: with these in place I can start a session, go teach or sit in a meeting, check in from my phone, and come back to finished work I can actually verify.
