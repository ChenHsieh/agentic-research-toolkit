Running it locally

Can you do all this with a model on your own machine, with nothing leaving it? Partly. Here's what works, what doesn't yet, and the setups in between.

The short answer

  • Local chat: realistic today. Summarizing, rewording, explaining code, drafting notes, on a recent laptop.
  • Local agent on small, well-defined tasks: workable. Edit this script, write this function, fix this error.
  • Local agent running a multi-hour research session: not yet, for most people. Planning, keeping track of many files, noticing that a result is wrong: this is where the gap to the best hosted models is widest, and it's exactly the part research needs.

Why: speed is set by memory

When a model writes text, every word requires reading all of its weights from memory. So speed is roughly:

speed ≈ memory bandwidth ÷ model size

Measured on a base M4 Mac (about 100 GB/s), with 4-bit models:

  • 3B model (~1.7 GB): 55 tokens/s
  • 7B model (~4 GB): 24 tokens/s
  • 7B at 8-bit (~7.5 GB): 13 tokens/s

Small models are fast but make more mistakes. Bigger ones are better but need more memory and get slower. An agent also reads a lot (files, logs, long instructions) before it writes anything, so a session feels slower than chat. More memory bandwidth (Pro/Max/Ultra chips, or a GPU) helps directly. I wrote a small tool that predicts this from a model's config before you download it.

Setups in between

  C --> D["Fully local

  • Hosted plans, local builds. The strong model writes the plan and reviews; a local model does the routine edits (I tried this with Aider). Saves cost; quality depends on how small the steps are.
  • Hosted model, local data. The agent works on code and on summaries or a de-identified subset, never the sensitive raw data. Often the most practical option for protected data.
  • Your institution's GPUs. An open model on a university cluster GPU is "local" in the sense that matters (data stays in-house) and is much bigger than a laptop can run. Ask your research computing group what is allowed.
  • Fully local. Right when data truly cannot leave, or you have no internet. Expect to break tasks into smaller pieces and check more.

How to decide

  1. Start from the data, not the model. What are you allowed to send where? Check your institution's and funder's rules, and your lab subscription's terms. See Protect your data.
  2. If hosted is allowed, use it for the hard parts. It's where the time savings are.
  3. If it isn't, use a local or in-house model and shrink the tasks: one script, one question, one figure at a time, with you as the planner.
  4. Whatever you choose, test it on a task you already know the answer to.

This changes fast. Open models improve every few months, so re-test once or twice a year rather than settling the question for good.
