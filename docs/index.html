Using an agent for research

Chen Hsieh, October 2026. Plant genomics PhD student, University of Georgia. Code and files at github.com/ChenHsieh/agentic-research-toolkit.

People keep asking me how I use Claude Code for research. This is the answer. It is one page because the answer is short, and because most of what I could add would be decoration.

What it is

An agent is a program that runs a language model in a loop with a terminal. You type what you want. It reads files, writes code, runs it, reads the error, fixes it, runs it again, and tells you what happened. The difference from chat is that it does things rather than describing them.

I run it on the university cluster, in a terminal, inside tmux, in the folder of whatever project I'm on. I leave it running and check on it from my phone between other things. Several run at once, one per project.

That is the whole setup. There is nothing else to install. The rest of this page is about what goes wrong and what I do about it.

What I ask it to do

Catch me up on a project I haven't touched in a week. Run an analysis end to end, including writing and submitting the cluster jobs. Take the questions I got after a talk and work out which ones we can answer with data we already have. Redo the figures with the sample size on every panel. Read a lab's last five papers and tell me what they treat as standard. Rebuild my results from the Methods text alone, in an empty folder, and tell me where the text was not enough. Write the week's update for my advisor.

In short, the work of a good research assistant who never sleeps, types very fast, and is confidently wrong about one thing in ten. The last part is the part that matters.

The one thing I learned

I wrote down the rules. The agent reads a file called CLAUDE.md when it starts, and mine says where the data lives, what never to delete, how to submit jobs, how figures should look, and which mistakes have already happened. Every time it did something I didn't want to see again, I added a line.

That file grew to several hundred lines and the mistakes kept happening anyway. On one day in September, three defects shipped in one project that the file already forbade in plain words. A control that was matched on the wrong quantity. A null result read as evidence from an arm that could not have moved. A correlation pooled across groups that reversed sign within them.

The agent had read the rules. So had I. The problem is that the moment a rule applies gives no signal that it has arrived. Nobody goes looking for the rule about pooled correlations while they are computing a correlation, because it feels like computing a correlation, not like a situation with a rule.

So now the rules that matter are code. A script refuses to report a null without a power check. A hook refuses to let a session commit inside a shared checkout. A save function refuses a figure with no sample size on it. The rule fires whether or not anyone remembered it.

That is the only general lesson I have. Don't try to remember the rules. Run them.

What broke

I'll list these because each one cost something.

A comparison came back empty, and the summary reported it as passed. Nothing compared to nothing is not a difference. Now every control has to produce a number before the result counts.

Two sessions were working in the same folder. One committed the other's half-finished edits. Now each session gets its own copy of the repository, and a hook blocks the alternative.

A website I maintain kept serving results that had been withdrawn upstream, for four days, with every check green. Every check compared the site to itself. Now the build reads each source's corrections log first.

A job finished 25 minutes of GPU work and then crashed while printing the summary, before it had saved anything. Save first. Print second.

A result looked strong when each gene counted separately and vanished when related genes were grouped. The agent will not notice this on its own. You have to name the unit before you count.

Rebuilding my own results from the Methods text found a software setting I had never written down. With the default instead, about five percent of the genes in a key table changed category. I knew the setting. That is why I never wrote it down.

Long sessions

A session that runs for hours forgets. Old parts of the conversation get summarized, and the numbers and decisions from three hours ago drop out. So anything that matters goes in a file: a brief before starting, a task list during, a status file and a commit after each real step. When the session ends, a fresh one reads the files and the commits and tells me what was actually done. I trust that more than the summary written by the session itself, which is a story about what it believes it did.

Jobs that take hours don't need an agent watching them. The cluster scheduler can chain them. An agent that polls a queue every minute is spending money to wait.

Which model

The strongest one you have, for anything where being wrong is expensive, which in research is almost everything. The cost difference between models is small next to a wrong result you act on. Use the cheaper ones for volume, then have the strong one check. And test on a task you already know the answer to, not a leaderboard.

Fully local, with nothing leaving your machine, works for chat and for small, well-defined edits. It does not yet work for a multi-hour session on a real project. A seven-billion-parameter model on a laptop writes about 25 words a second and is noticeably worse at exactly the part research needs: noticing that something is wrong. If your data cannot leave, use the hosted model on code and summaries and keep the raw data out of its reach, or run an open model on your institution's GPUs.

Where to start

Install it. Open it in a folder you already understand. Ask it to tell you what every file does and what order to run them in. You know the answer, so you will know how good it is.

Then write five lines of CLAUDE.md. Then give it a real task. Then check the result the way you would check a new student's. When it does something you don't like, add a line. When a line stops working, turn it into code.

The agent does the typing. What's worth doing, and whether the answer is right, is still you. That part was always the job.
