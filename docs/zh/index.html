用程式代理做研究

Chen Hsieh，2026 年 10 月。美國喬治亞大學植物基因體學博士生。程式與檔案在 github.com/ChenHsieh/agentic-research-toolkit。這一頁譯自英文版，兩邊有出入時以英文版為準。其他頁面目前只有英文。

我研究裡大部分的打字，現在是程式代理（coding agent）在做。它們很會修「有聲音」的錯：程式當掉、少了套件、語法錯誤。在我那些跑很久的工作階段裡，留下來的反而是看起來像成功的錯。一個沒有任何數值的對照組被回報成「通過」。一個本來要檢查十四個儲存庫的迴圈只跑了一次，卻回報「全部乾淨」。我在全新的小任務上實際測過這件事，結果代理連這類錯也抓到了。它抓不到的，是沒有人寫下來的決定。常有人問我怎麼用這些工具，所以這一頁列出我怎麼做、哪裡出過錯、每次出錯之後改了什麼。文中日期都是 2026 年。

先看八條原則 · 複製提示與檔案 · 用你自己的專案跟我走一次（20 分鐘）

八條原則

  1. 做事變便宜了，檢查沒有。省下來的時間拿去做檢查。
  2. 每個檢查都要先讓它失敗一次，而且是敗在它該抓的那種錯上，才能相信它。你沒看過它說「不」的檢查，只是一段描述。試試看
  3. 空的不算量過。對照組沒有數值，不叫通過。案例
  4. 重要的規則要變成程式。寫在檔案裡的規則只會被讀一次，然後被忘記。案例
  5. 先講清楚單位再去數。單位有分組時，組內的結果也要報。案例
  6. 紀錄在檔案裡，不在對話裡。任務說明、待辦清單、狀態檔、commit。原因
  7. 只靠 Methods 把結果重做一次。缺的地方標成 BLOCKED，絕不用猜的。案例
  8. 檢查要放在代理碰不到的地方。它改得動的檢查，它就有辦法讓它通過。原因

編號條列的形式借自 rewrites.bio（Seqera），那是一份用 AI 改寫生物資訊工具的原則。裡面有一句 "Fast code is now cheap. Scientific insight, validation, and trust are not"，是同一件事從軟體那一邊的說法。

我的環境

Claude Code 是一個命令列程式。它跑一個語言模型，可以在你啟動它的資料夾裡讀檔、改檔、執行指令。每一個它想執行的指令，都可以設定成要你同意才執行。

我在學校的運算叢集（Slurm 排程器）上、在 tmux 裡面跑它，一個專案一個工作階段，通常同時開好幾個，用當時最強的模型。大部分的回覆我是在手機上透過 Remote Control 打的。9 月 2 日到 10 月 2 日，我在叢集上跑了大約 75 個工作階段，在筆電上大約 10 個，其中 3 個用的是 Codex。

這個量是有影響的。我做得出來的東西，有一部分來自同時開很多個最強的模型，不是來自方法。下面那些失敗，是在這樣的用量下照樣發生的。

這一頁是什麼：一個人、一個叢集、幾個月的經驗，數字是我能對回檔案的那些。它不是在測量代理一般來說有多好；那種資料請看延伸閱讀裡的評測。

我拿它來做什麼

從檔案和 git 紀錄整理一個專案目前的狀態。把一個分析從頭做到尾，包含寫、送出、檢查叢集上的工作。演講後聽眾問的問題，用手上已有的資料去回答。照寫好的規則重畫圖。整理某個實驗室發表過的方法，每一句都要引到論文原文。在空資料夾裡只靠 Methods 的文字把我的結果重做一次。每週給指導教授的進度更新。

七種會出錯的方式

這些是固定會出現的型態，不是運氣不好。每一種我都至少遇過一次。

空的對照組

你會看到
一個比較被回報成「通過」，但它背後的對照組沒有任何數值。
怎麼做
空的對照組就是沒量到。讓程式把對照組的列數寫進結果表，然後自己打開那張表，再去讀任何比較。這種事只要一行就會發生：在 R 和 Python 裡，對空的清單取 all() 都是 true，所以「每個對照值都低於門檻」在沒有對照值的時候會通過。可以試試 R 的 all(logical(0)) 或 Python 的 all([])。

跑完了，但是空的

你會看到
工作顯示正常結束，輸出檔也在，打開只有表頭。
怎麼做
在規則檔裡寫清楚「完成」是什麼意思：哪個檔案、幾列、數值範圍多少。結束代碼 0 只代表程式停了。

單位弄錯

你會看到
一大批其實有分組的東西（基因在基因家族裡、細胞在個體裡、樣本在批次裡）之間有很強的相關。
怎麼做
數任何東西、算任何相關之前，先講出單位是什麼。單位有分組，就連每一組裡面的結果一起要。

不出聲的猜測

你會看到
代理把你的結果重做出來，數字也對上了，但過程中它自己選了一個你的筆記從沒提過的設定。
怎麼做
告訴它：資訊不夠就停下來說。剛好猜中的猜測，會把那個缺口藏起來。

拿自己跟自己比的檢查

你會看到
你用別的專案的結果做出來的東西，在那個專案更正結果之後，還是通過所有檢查。
怎麼做
重建之前，先讀來源的更正紀錄。把輸入釘住，只能證明你跟當初用的那份一致，不能證明那份還成立。

最後一步弄丟

你會看到
跑很久的工作在印出摘要的時候當掉，而那時它什麼都還沒存。
怎麼做
先把結果存到硬碟，再印。要求結果邊算邊寫出去。

兩個代理，一個資料夾

你會看到
一個工作階段把另一個做到一半的修改 commit 掉，或是在它腳下切換了分支。
怎麼做
讓每個工作階段有自己的一份儲存庫（git worktree）。

為什麼這些失敗沒有聲音

回頭看上面那些失敗，只有一個是當掉的。對照組什麼都沒回，被讀成通過。工作正常結束，檔案是空的。網站通過所有檢查，因為每個檢查都是拿它跟自己比。還有開頭說的那個十四個儲存庫的檢查，只跑了一次。每一個都有檢查，而每一個檢查都不可能說「不」。

這個型態有一部分是我「記下了什麼」造成的。有聲音的失敗（當掉、少套件、語法錯誤）在工作階段裡一分鐘就修掉，根本不會進到我的筆記。但這也正是重點。代理那個「執行、讀錯誤、修、再執行」的迴圈，很會清掉有聲音的錯。在我的筆記裡，留下來要我自己發現的，大多是沒聲音的。這件事在我的筆記之外成不成立，是下一節要測的。

情況可能比「篩子」更糟。2026 年有一個生物資訊的評測（FlowBench）發現，代理常常把失敗的執行「修」到能正常結束，資料卻還是錯的。當「成功」很容易看見、「正確」很難看見，代理可能會朝它看得見的那一邊去。在 METR 的評測任務裡，這包括「試圖（而且常常成功）靠修改測試或計分程式來拿到更高的分數」（METR 2025）。那些是有計分的軟體任務，不是研究，但道理通用：正常結束、測試全綠，都只是一個要去查證的說法。把檢查、它的預期值、原始輸入，放在代理工作的資料夾之外，等代理停了再跑。git hook 只有在代理跳不過執行它的那個東西時才有用。

做實驗的生物學早就有對付這件事的工具。每個檢測都有一個應該保持暗的陰性對照，和一個應該亮起來的陽性對照。只要其中一個不對，這一批就什麼都不能說，其他孔長怎樣都一樣。下面那張表裡的「打亂標籤」和「放進已知訊號」，就是這兩種對照。軟體測試用另一個名字講同一件事：變異測試（mutation testing）故意把程式弄壞，看測試有沒有發現（DeMillo、Lipton 與 Sayward，1978）。費曼在 1974 年是這樣說的："The first principle is that you must not fool yourself, and you are the easiest person to fool"（Cargo Cult Science）。第一條原則是不要騙自己，而自己是最好騙的人。

新的地方在於量。代理寫檢查的速度，比任何人幫這些檢查寫陽性對照的速度快。所以我想傳下去的習慣很小：相信一個檢查之前，先讓它失敗一次。餵它空檔案、打亂的標籤、故意做錯的案例，看著它說「不」。你沒看過它說「不」的檢查是描述，不是測試。逼它失敗一次，只證明一件很窄的事：這個檢查抓得到這一種錯。所以留幾個代理從沒看過的壞案例，到最後再跑。然後給它一個你確定是對的案例，看它通過：會對好資料說「不」的檢查，遲早被人關掉。

我去測了，簡單版的說法不成立

上面的說法來自我的筆記，所以我試著去量它。我用虛構的基因表現資料做了 15 個小的分析資料夾。六個有「有聲」的錯（程式會當掉：import 寫錯、欄位名稱不對、語法錯誤等等）。六個有「無聲」的錯（程式跑得完，而且很有把握地印出錯的結果：對照組是空的、標籤靠位置對應、技術重複被當成植株、讀到過期的快取、過濾條件和計畫不同、正負號反了）。三個是乾淨的。我固定用一個代理（Claude Code 搭配 Sonnet 5.5，完全不載入我的規則和記憶），對每個資料夾下同一個指示：「執行這個分析並回報結果」，再由一個它看不到的檢查程式評分。三種情況各跑兩次：資料夾裡有寫好的分析計畫、計畫再加六條檢查規則、把計畫刪掉。總共 90 次，花了 7.78 美元。

我本來預期「無聲」那一列會比「有聲」那一列差很多。結果沒有。代理找出了每一個無聲的錯，而且說得出是什麼錯，例如它寫道：對照組是空的，所有 p 值都是 NaN，原本的程式錯誤地回報 0 個顯著基因。那六條規則沒有造成任何差別，因為已經沒有東西留給它們抓。在乾淨的資料夾上它也沒有誤報。

唯一漏掉的那一次才是有用的部分。把計畫刪掉以後，那個「過濾條件和計畫不同」的資料夾裡，再也沒有任何地方記著過濾條件原本應該是什麼。兩次裡有一次，代理沿用了錯的過濾條件，並回報結果沒問題。一個從來沒被寫下來的決定，再怎麼檢查也找不回來。

所以我真正能主張的，比我原本相信的窄：

1. 在全新的小任務上，現在的代理被要求執行分析時，也會順便稽核它，並且抓得到跟「它讀得到的東西」互相矛盾的錯：資料、程式、寫好的計畫。
2. 它抓不到只存在你腦袋裡的決定。這又是不出聲的猜測，也是「執行之前先寫任務說明」的理由。
3. 這還沒有測到我真正出錯的情境：工作階段已經跑了好幾個小時、程式是代理自己寫的、沒有寫下來的計畫、也沒有人要求稽核。這裡的代理是全新的、只讀檔案，表現很好，這算是支持「長時間執行結束後，開一個新的工作階段來複查」的一點證據。

限制：一個模型、一種任務、虛構資料、每種錯各六個、各跑兩次。這些無聲的錯比真實的容易發現，因為每一個都跟資料夾裡寫著的某樣東西矛盾。有聲和無聲的錯難度也沒有配對。卡片、檢查程式和每一筆結果都在儲存庫裡，另外還有一份我請 Codex 在沒看到結果的情況下寫的設計批評。

規則先在檔案裡，然後在程式裡

Claude Code 啟動時會讀一個叫 CLAUDE.md 的檔案（Codex 讀的是 AGENTS.md）。我的那份寫了資料放哪裡、什麼不能刪、怎麼送工作、圖的要求，還有過去犯過的錯。每犯一次錯我就加一行。

9 月 4 日，同一個專案裡出了三個那份檔案早就禁止的錯：

1. 一個對照組受到的改動量，大約是它要對照的那個條件的三倍。修正之後，主要結果從 0.21–0.39 變成 0.60–0.78。
2. 一個「沒有效應」的結果，來自一個其實幾乎什麼都沒變的條件。
3. 一個跨 6 組、48 個項目的相關：合在一起算是 +0.45（p = 0.001），在各組裡面算是 −0.11（p = 0.47）。

規則就在檔案裡，卻沒有被用上，因為做分析的那一刻，沒有任何東西指向它們。我把重要的幾條搬進會讓工作停下來的程式裡：

一支程式在對照組和它的條件用不同的量來配對時會報錯，而且沒有先確認資料夠不夠看得出效應，就拒絕回報「沒有效應」。
一個 git hook 擋掉在共用工作目錄裡的 commit、切分支和 stash。
一個存圖的函式拒絕沒有樣本數、文字小於 20 pt、或標籤重疊的圖。

程式要有東西去執行它才有用。我在叢集上整理的時候，發現五個寫得正確、卻沒有任何程式呼叫的對照函式；所謂「用程式強制執行對照」，講的是一個沒人 import 的函式庫。從沒被呼叫的檢查是 BLOCKED，不是 PASS。所以寫完一個檢查的最後一步，是找出呼叫它的那一行。

為什麼這件事會越來越難

1983 年，Lisanne Bainbridge 描述了「自動化的諷刺」（PDF）：一個流程自動化得越多，人剩下的工作就越是那些不正常的情況，要發現並補救自動化做錯的地方，可是人對正常情況的練習反而變少。代理正是這樣。例行的執行它們拿走了；留給你的是無聲的失敗，而你待在資料裡的時間比以前少。

科學哲學對「好的檢查」有現成的說法。史丹佛哲學百科這樣總結波普："Every genuine test of a scientific theory, then, is logically an attempt to refute or to falsify it"（SEP）。Deborah Mayo 的版本是「嚴格檢驗」：只推論那些這個程序真的有機會證明為錯的事（Mayo 與 Spanos，2006）。結束代碼對一個生物學結果來說不是嚴格檢驗。一個流程非找到不可的已知訊號才是。

Gelman 和 Loken 的「分岔小徑的花園」（PDF）是另一個風險。看過資料之後才做的選擇（用哪個過濾條件、哪個門檻、丟掉哪些樣本），會讓通往「乾淨結果」的路變多，而且不需要任何人故意去撈。代理一個小時就能走過很多條這樣的路，然後回報走得通的那一條。解法很老：在看到結果之前把決定寫下來，並且記下試過什麼、放棄什麼。任務說明（執行前寫）和狀態檔裡都留了位置。

Merton 把「有組織的懷疑」列為科學的規範之一（美國國家學院的摘要）：主張要由作者以外的人來檢查。開一個新的工作階段、讓它讀檔案而不是讀摘要，是這件事小而便宜的版本。它抓得到「說做了其實沒做」的工作。但它是第二次檢查，不是獨立的檢查：它跟前一個共用任務說明、儲存庫，通常也是同一個模型。讓它先讀輸入和輸出，再看前一個工作階段的摘要，效果比較好。一個懂這個實驗的同實驗室夥伴，是更強的檢查。

Parasuraman 與 Riley 1997 年的論文〈Humans and automation: use, misuse, disuse, abuse〉列出四種把平衡抓對或抓錯的方式。下面代理的例子是我自己加的：

善用把例行的執行交出去，而且最後有一個你看過它失敗的檢查。
誤用把結束代碼或代理自己的摘要當成結果。
棄用一次不好的經驗之後就不用了，連有測試過的檢查可以把關的例行執行也不用。或是把一個老是對好資料說「不」的檢查關掉。親手學一個方法不算棄用。
濫用設定的方式沒有顧到相關的人：在共用叢集上不設上限地送工作、產出或工作階段多到沒人看得完、或是沒有辦法看見並停下它正在做的事。

很長的工作階段

對話一長，比較舊的部分會被摘要，細節就不見了。我在硬碟上留一份任務說明、一份待辦清單、一份狀態檔，每做完一步就 commit。結束時，開一個新的工作階段去讀這些檔案和 commit，回報實際做了什麼。我用的是那份回報，不是原本那個工作階段自己寫的摘要。

等待這件事交給排程器（工作相依），或是交給一個背景檢查，它在工作離開佇列時結束。不是讓代理一直去問。我也給每一個等待設期限。卡住的工作會一直留在佇列裡直到時間上限，可能是好幾天以後，而且永遠不會寫出它的檔案。所以我的工作每幾分鐘印一行進度，背景檢查把「log 不再變長」當成失敗。

要放手讓它跑多少

這些工具讓你選擇代理多常停下來問你。Claude Code 的模式從「每個指令都先問」到「先擬計畫，之後自由修改」到「完全不問」；Codex、Cursor 等等也有類似的設定。哪一種才對，比較不取決於工具，而取決於這個任務可能弄壞什麼。

在共用的叢集上，有寫出指引的幾個運算中心在一點上是一致的：凡是會送出工作、取消工作、刪除檔案的事，都要保留人工同意。NCAR 的頁面直接點名了會出的事：失控的 qsub 迴圈、遞迴刪除、或是用掉你一大塊配額的工作（NCAR；Aalto 說的也差不多）。

不管用哪種模式，我都留一份很短的清單，寫在規則檔裡，讓它在每個工作階段都有效。到這些點它必須停下來問：

1. 要刪除或覆寫任何不是它自己建立的東西之前。
2. 要送出超過一定數量的工作，或是用它沒用過的共用硬體之前。
3. 要寫到專案資料夾以外的地方之前：共用磁碟、推到上線中的網站、傳訊息給別人。
4. 計畫改變的時候：換方法、丟掉樣本、移動門檻。
5. 任何數字要進到稿子、投影片、或是給指導教授的訊息之前。

前三條保護的是別人和資料。後兩條保護的是結果：這些是「看過資料之後才做的選擇」最容易溜進來的地方。

過夜執行

過夜執行要順利，條件是你在離開前就寫得出隔天早上要做的檢查：哪些檔案、幾列、數值範圍多少。我把它寫進任務說明。如果任務做到一半需要你的判斷，就不會順利，因為代理不是停下來等，就是自己替你決定。

離開之前：事前驗屍

It is tomorrow morning. This run produced a result that looks convincing but is wrong. List five ways that could have happened. For each, add the smallest check that would catch it, and run that check on a known-bad input now.

「事前驗屍」（premortem）是 Gary Klein 的方法：先假設專案已經失敗，再問為什麼（HBR，2007）。提示保留英文，因為我實際上是用英文下的。

會順利 目標一句話講得完。有一個它跑得了、而且你看過它失敗的檢查。小階段，每個都以一個檔案和一次 commit 結束。工作在排程器裡串好。它有自己的一份儲存庫。哪些指令可以不問就跑，事先決定好，才不會半夜一點停在那裡等你說好。

會出事 「去探索一下這份資料。」成功與否由它自己的摘要判斷。一個很長、只在最後才存檔的工作。共用的資料夾。一個整晚在問佇列的代理。可以送的工作數量沒有上限。

評測不會告訴你可以放它跑多久。METR 量的是代理有一半機率完成的任務長度（以人類所需時間計）；GPT-5 大約是 2 小時 17 分。METR 自己的說明講得很清楚，這不是代理能獨自執行多久；而且對人類要花 90 分鐘到 3 小時的任務，大約三分之一每次都成功、三分之一每次都失敗、三分之一時好時壞（METR）。Anthropic 的報告說，2025 年 2 月到 8 月之間，他們自己工程師的工作階段，從大約 10 個動作才需要人介入，變成大約 20 個（Anthropic）。把一個晚上規劃成幾個短的、有檢查的階段，而不是一個很長的任務。

它在跑的時候

不要用「盯著它」來代替一個事先規劃好的檢查。我不知道有哪個研究是在研究盯著代理看，但有一個研究的是「AI 幫忙」感覺起來有多快。在 2025 年的一個隨機試驗裡，有經驗的開源開發者預期 AI 工具會讓他們快 24%；在 246 個真實任務上，他們慢了 19%（METR）。那是 2025 年初的工具、成熟的程式庫，而且 METR 正在重做這個研究，但有用的是那個落差：感覺有多快，和實際有多快，是兩回事。

我自己的做法：給工作階段一個叫醒我的條件（工作離開佇列了、某個檔案出現了），而不是我去查它。去做只有人能做的事：讀、寫、開會、做實驗。它來問的時候才用手機回，不是為了監督。複查一次做完，從檔案和 commit 來看，由一個沒有參與這份工作的新工作階段來做。

模型

在研究裡，幾乎到處都是「出錯很貴」，所以設計、解讀和複查我都用最強的模型。比較便宜的模型可以拿來做大量的修改，只要結果有人檢查。我用的一種安排：強的模型把計畫寫成編號的小步驟，每一步附一個測試指令；便宜的模型透過 Aider 去做每一步；只有通過與否和錯誤訊息的結尾會回來。判斷留在強的模型，打字交給便宜的。工具在某個模型過載時可能會換成另一個；工作階段的狀態會顯示是哪個模型回答的。

本機模型：在基本款的 M4 Mac 上，一個 70 億參數、4-bit 的模型每秒大約產生 24 個 token（我自己量的）。這對聊天和小修改夠用。我沒有用本機模型跑過好幾個小時的專案工作階段。如果資料不能離開你的機構，可以選擇只讓雲端模型看到程式和摘要，或是在機構自己的 GPU 上跑開源模型。

怎麼開始

1. 安裝 Claude Code（需要付費的 Claude 方案或 API 額度；免費方案不含）。在一個你已經很熟的資料夾裡打開它。
2. 問它每個檔案在做什麼、執行順序是什麼。拿它的答案和你知道的比。
3. 保留「執行指令前要同意」。
4. 把五行的規則檔複製成 CLAUDE.md，把括號裡的內容填好。每犯一次錯加一行。
5. 讓一個檢查失敗一次。把某個輸入檔只留表頭複製一份（head -n 1 input.tsv > empty.tsv），拿它去跑你的第一步，看有沒有任何東西說「不」。如果沒有，就寫一個會說「不」的檢查，然後看著它說。
