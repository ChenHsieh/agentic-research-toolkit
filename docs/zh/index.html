我怎麼用 AI 代理做研究

Chen Hsieh，2026 年 10 月。美國喬治亞大學植物基因體學博士生。程式與檔案放在 GitHub。本頁依英文版改寫；內容若有出入，以英文版為準。其他頁面目前仍只有英文。

現在我研究裡大部分的打字，都是 coding agent（以下簡稱代理）在做。它很會修會直接噴錯的 bug，像程式當掉、缺 module、語法錯。不過長 session 跑下來，最後留下的通常是表面正常、其實錯了的 bug：沒有任何數值的對照組被回報為通過；原本要檢查十四個 repository 的迴圈只跑了一次，卻說全部沒問題。我後來用新的小任務實測過，代理其實連這類錯也抓得到。它抓不到的是沒人寫下來的決定。有人問過我平常怎麼用這些工具，所以把做法、出過的錯，還有每次之後改了什麼整理在這裡。文中日期皆為 2026 年。

先看八個原則 · 複製 prompt 與檔案 · 用你的專案實作一次（20 分鐘）

八個原則

  1. 做事變便宜，檢查沒有。省下的時間要拿來做檢查。
  2. 每個檢查都先讓它失敗一次。而且要是它本來就該抓到的錯。沒看過它說「不」的檢查，只是一段說明。試試看
  3. 空的不算有量到。對照組沒有數值，不能算通過。案例
  4. 重要規則要寫進程式。規則只寫在檔案裡，讀過一次就很容易被忘掉。案例
  5. 數之前先講清楚單位。單位有分組，就要報各組裡的結果。案例
  6. 紀錄要留在檔案和 commit，不要只留在對話。brief、task list、STATUS.md、commit。做法
  7. 只靠 Methods 重做一次結果。缺資料就標 BLOCKED，不要猜。案例
  8. 檢查要放在代理改不到的地方。它能改的檢查，就可能被它改到通過。原因

這種編號條列的寫法借自 rewrites.bio（Seqera），它談的是用 AI 重寫生物資訊工具的原則。其中一句是 "Fast code is now cheap. Scientific insight, validation, and trust are not"，從軟體那一端講的是同一件事。

我怎麼跑

Claude Code 是命令列工具，裡面跑的是語言模型。它能在你啟動它的資料夾裡讀檔、改檔、跑 shell command；每一個 command 都可以設成要你同意才執行。

我在學校叢集上透過 tmux 跑它，叢集用 Slurm 排程。一個專案一個 session，通常同時開好幾個，選當時最強的模型。大部分 prompt 我用手機透過 Remote Control 回。9 月 2 日到 10 月 2 日，我在叢集上大約跑了 75 個 session，筆電上大約 10 個，其中 3 個用 Codex。

這個量很重要。我能做出多少東西，有一部分是因為同時開了很多個最強模型，不是因為這套方法有什麼神奇。下面的失敗，在這種用量下還是照樣發生。

這頁只是我一個人在一個叢集上用幾個月的經驗，數字都是我能回頭對檔案的。它不是在量代理整體表現；那類資料請看延伸閱讀裡的 benchmark。

我拿它來做什麼

我會拿它根據檔案和 git history 整理專案現況；把分析從頭跑到尾，包括寫、送、查叢集 job；用現有資料回答演講後的問題；照書面規格重畫圖；整理其他實驗室發表的方法，每個主張都附原文引句；在空資料夾裡只看 Methods 重做自己的結果；還有寫給指導教授的每週進度。

七種常見的出錯方式

這些不是剛好倒楣，而是會反覆出現的模式。每一種我至少都遇過一次。

空白的對照組

你會看到
比較被回報為通過，但背後的對照組根本沒有數值。
怎麼做
對照組是空的，就代表沒量到。讓程式把對照組列數寫進結果表，自己先打開那張表，再看任何比較。這個問題一行程式就會發生：R 和 Python 對空 list 做 all() 都回傳 true，所以沒有任何對照值時，「每個對照值都低於門檻」還是會通過。可試試 R 的 all(logical(0)) 或 Python 的 all([])。

job 跑完，結果是空的

你會看到
job 顯示正常結束，輸出檔也在，打開卻只有表頭。
怎麼做
在規則檔寫清楚「完成」是什麼：哪個檔案、幾列、數值範圍。exit code 0 只表示程式停了。

分析單位弄錯

你會看到
明明有分組的項目，合在一起後出現很強的相關，例如基因家族裡的基因、同一隻動物的細胞、不同 batch 的樣本。
怎麼做
要數東西或算相關之前，先說清楚分析單位是什麼。單位有分組時，也要報各組裡的結果。

悄悄補上的設定

你會看到
代理重做出你的結果，數字也對上，但過程中它自己選了一個筆記從沒提到的設定。
怎麼做
明講資訊不足時要停下來說。剛好猜對的設定，會把真正的缺口藏起來。

檢查拿自己比自己

你會看到
你拿另一個專案的結果做出的東西，在來源專案更正結果後，仍通過所有檢查。
怎麼做
重建前先讀來源的 correction list。把 input pin 住，只能證明你和當初的輸入一致，不能證明它現在還對。

最後一步才當掉

你會看到
長 job 在印摘要時當掉，前面算出的東西卻都還沒存。
怎麼做
先把結果存到磁碟，再 print。要求結果一產生就寫出去。

兩個代理共用一個資料夾

你會看到
一個 session 把另一個還沒做完的修改 commit 掉，或在它底下切走 branch。
怎麼做
每個 session 都給自己的 Git worktree。

為什麼這些錯看起來都正常

回頭看上面的例子，只有一個真的當掉。空白對照組被當成通過；job 正常結束卻留下空檔；網站通過所有檢查，因為每一項都是拿自己和自己比；開頭那個要查十四個 repository 的迴圈，也只跑了一次。它們都有檢查，但那些檢查根本不可能說「不」。

這個模式有一部分是我的紀錄方式造成的。會直接噴錯的 bug，像 crash、缺 module、syntax error，通常在 session 裡一分鐘就修掉，不會進筆記。但這也正是重點：代理很會跑「執行、讀 error、修正、再跑」這個迴圈。我的筆記裡剩下要自己發現的，大多都是表面正常、其實錯了的 bug。下一節會測，這件事離開我的筆記後還成不成立。

事情可能不只是漏網而已。2026 年的生物資訊 benchmark（FlowBench）發現，代理常把失敗的 run「修」到正常結束，但資料其實還是無效。當成功很容易看見、正確很難看見，它可能只會追逐前者。METR 的 benchmark task 裡，也出現過「試圖（而且常常成功）靠修改測試或計分程式來拿到更高的分數」（METR 2025）。那些是有分數的軟體任務，不是研究，但道理一樣：正常 exit 或全綠的 test，都只是需要再查的主張。把 check、預期值和原始 input 放在代理工作目錄外，等它停下後再跑。git hook 只有在代理不能跳過觸發它的東西時才有用。

實驗生物學早就有這套工具。每個 assay 都有該保持暗的 negative control，和該亮起來的 positive control。只要其中一個不對，這一批其他孔看起來再漂亮都不能說明什麼。下表的「打亂標籤」和「放進已知訊號」就是這兩種 control。軟體測試也有同樣的想法，叫 mutation testing：故意把程式弄壞，看看 test 有沒有發現（DeMillo、Lipton 與 Sayward，1978）。費曼在 1974 年說過："The first principle is that you must not fool yourself, and you are the easiest person to fool"（Cargo Cult Science）。第一條原則是別騙自己，而人最容易騙的就是自己。

新的地方是量。代理寫 check 的速度，比人替那些 check 準備 positive control 還快。我想留下的習慣很簡單：信一個 check 以前，先讓它失敗一次。拿空檔、打亂的標籤、刻意做錯的案例餵它，看它說「不」。沒看過它說「不」的 check 是描述，不是 test。強迫它失敗一次，只能證明一件很窄的事：這個 check 抓得到這個 fault。所以最後還要跑幾個代理沒看過的壞案例。也要給它一個你確定正確的案例，看它會不會通過，因為對好資料一直說「不」的 check 最後一定會被關掉。

我實測過，但原本想得太簡單

上面的說法只是我的筆記，所以我想量看看。我用虛構的 gene expression data 做了 15 個小分析資料夾。六個放進會直接噴錯的 bug，像 import 寫錯、欄位名不對、syntax error。六個放進表面正常、其實錯了的 bug：空白對照組、標籤按位置配對、把 technical replicate 當植株、讀到舊 cache、filter 和計畫不一致、正負號顛倒。三個是乾淨的。固定用一個代理，Claude Code 搭配 Sonnet 5.5，不載入我的規則或記憶，對每個資料夾下同一句 brief：「執行這個分析並回報結果」，再由它看不到的 checker 評分。每種條件跑兩次：資料夾裡有分析計畫、有計畫加六條檢查規則，或把計畫刪掉。共 90 次，花 $7.78。

我原本以為表面正常的 bug 那列會明顯比較差，結果沒有。代理找出所有這類 bug，也講得出問題在哪，例如：「對照組是空的，所有 p-values 都是 NaN（script 錯誤地回報 0 個顯著基因）」。六條規則沒有改變結果，因為已經沒有 bug 留給它們抓。它在乾淨資料夾上也沒有誤報。

真正有用的是唯一漏掉的那次。計畫被刪掉後，那個 filter 和計畫不一致的資料夾裡，已經沒有地方記錄 filter 本來該長什麼樣子。兩次裡有一次，代理沿用錯 filter，還回報結果沒問題。從來沒寫下來的決定，再多 check 也救不回來。

所以真正有證據支持的，比我原先相信的更窄：

1. 在新的小任務上，現在的代理被要求跑分析時，也會順便 audit，抓得到和它讀得到的東西矛盾的錯：資料、程式、寫下來的計畫。
2. 它抓不到只存在你腦中的決定。這又回到悄悄補上的設定，也是為什麼要在 run 前先寫 brief。
3. 這還沒碰到我真實出錯的情境：session 已經跑了好幾小時、程式是代理自己寫的、沒有書面計畫，也沒人要求 audit。這裡表現好的是全新的代理，而且只讀檔案；這算是長任務結束後開新 session 複查的一點證據。

限制很明顯：只有一個模型、一種任務、虛構資料，每類六個 bug，每個跑兩次。表面正常的 bug 比真實情境容易發現，因為每一個都和資料夾裡寫著的某件事矛盾；兩類 bug 的難度也沒有配對。卡片、checker 和所有結果都在 repository 裡，另附一份 Codex 在沒看過結果時寫的設計批評。

規則不只寫在檔案裡，也要寫進程式

Claude Code 啟動時會讀 CLAUDE.md，Codex 讀的是 AGENTS.md。我的檔案寫著資料在哪、什麼不能刪、job 怎麼送、圖的要求，還有以前犯過的錯。每犯一次，就多加一行。

9 月 4 日，同一個專案出了三個 CLAUDE.md 早就禁止的錯：

1. 一個 control 的變化量約是它要 control 的 condition 的三倍。修正後，主要結果從 0.21–0.39 變成 0.60–0.78。
2. 一個「沒有效應」的結果，其實來自幾乎沒有變化的 condition。
3. 6 組、48 個項目合起來的相關是 +0.45（p = 0.001），各組內卻是 −0.11（p = 0.47）。

規則明明在檔案裡，分析當下卻沒有任何東西提醒它們。我把重要的幾條改寫進會直接讓工作停下來的程式：

一支 script 會在 control 和 condition 用不同 measure 配對時報錯；如果沒先確認資料夠不夠看出效應，就拒絕回報「沒有效應」。
一個 Git hook 會擋下在共用 checkout 裡的 commit、切 branch 和 stash。
一個存圖函式會拒絕沒有 sample size、文字小於 20 pt，或 label 重疊的圖。

程式有被跑到才有用。我整理叢集時發現五個寫得正確、但沒有任何 script 呼叫的 control function。所謂「control 寫進程式」其實只是一個沒人 import 的 library。沒被呼叫的 check 是 BLOCKED，不是 PASS。所以寫完 check 的最後一步，是找出哪一行真的會叫它。

為什麼反而更難

Lisanne Bainbridge 在 1983 年寫過「automation 的諷刺」（PDF）：流程越自動化，人剩下的工作越是不正常的 case，要發現並收拾自動化做錯的地方；但人練習正常 case 的機會反而更少。代理就是這樣。例行工作被它接走，留下的是表面正常、其實錯了的 bug，而你待在資料細節裡的時間比以前少。

科學哲學其實早就說過什麼是好的 check。史丹佛哲學百科這樣總結 Popper："Every genuine test of a scientific theory, then, is logically an attempt to refute or to falsify it"（SEP），也就是好的 test 在邏輯上是要試著推翻它。Deborah Mayo 把這叫 severe test：只能推論那些這套程序本來真有機會證明為錯的事（Mayo 與 Spanos，2006）。對生物學結果來說，exit code 不是 severe test；pipeline 非找到不可的已知訊號才是。

Gelman 和 Loken 的「forking paths garden」（PDF）是另一個風險。看過資料才決定 filter、threshold 或丟哪些 sample，會多出很多條走到漂亮結果的路，不必有人刻意挑結果也是如此。代理一小時能走過很多條，然後只回報走得通的那條。解法很老：看結果前先把決定寫下來，也記錄試過什麼、丟掉什麼。brief 是 run 前寫的，status file 則留後續紀錄。

Merton 把「organized skepticism」列為科學規範之一（美國國家學院摘要）：主張應該由作者以外的人檢查。開一個新 session，讓它讀檔案、不讀前一個 session 的摘要，是一個小而便宜的版本。它能抓到明明說做了、實際沒做的工作。但這只是第二輪，不是獨立檢查，因為它共用 brief、repository，通常連模型也相同。先讀 input 和 output，再看前一個 session 的摘要會好些。真正更強的 check，還是懂這個 assay 的實驗室同事。

Parasuraman 與 Riley 1997 年的論文〈Humans and automation: use, misuse, disuse, abuse〉整理了四種把人和自動化關係用對或用錯的方式。下面的代理例子是我加的：

善用把例行執行交出去，最後再用一個你看過它失敗的 check 收尾。
誤用把 exit code 或代理自己的摘要當成結果。
棄用一次不好的經驗後就完全不用，連有測試過的 check 能把關的例行工作也不交出去。或把老是對好資料說「不」的 check 關掉。自己親手學一個方法不算棄用。
濫用設定時沒顧到別人：在共用叢集無上限送 job、產出或 session 多到沒人看得完，或根本看不見、也停不下它正在做的事。

一切都靠 GitHub 串起來

每個交給代理的專案，我都放在一個 GitHub repo 裡，這頁大部分的習慣也都是透過它在運作。如果這頁只能帶走一件實際的事，就帶走這件。

commit 紀錄就是實驗紀錄本。我要求每做完一個實際的步驟就 commit 一次，訊息寫清楚改了什麼、為什麼。session 的摘要是它自己的說法；commit 才是實際發生的事。session 結束後，新的 session 讀的是 log 和 diff，不是對話。

它在不同機器之間搬工作。我的筆電和叢集沒有共用硬碟。程式、小的結果表和圖都經過 GitHub；叢集上的 job 拉下它該跑的那個 commit。報告裡的數字會附上它來自哪個 commit，而且要等 push 成功之後我才引用那個 commit。

它讓代理彼此隔開。每個 session 在自己的工作目錄裡做事（Git worktree，見兩個代理共用一個資料夾）。哪一個弄壞了東西，影響只留在它自己的 branch 上。

它是我給人看成果的方式。private repo 也可以從 docs/ 資料夾發布一個公開網站（GitHub Pages；public repo 免費，private repo 需要付費帳號）。我在第一個粗糙的版本就把它打開，讓指導教授或朋友用手機點連結就能看，不用 pull branch。這個網站就是這樣做的。repo 是 private，發布出去的網站仍然是公開的，所以 docs/ 裡只放可以公開的東西。

哪些不放進去。原始資料、大檔案和任何機密。大的輸出留在叢集的儲存空間，repo 裡只放一個指標：路徑、大小和 checksum。

長 session 怎麼收尾

對話一長，前面內容會被摘要，細節就掉了。我把 brief、task list、status file 留在磁碟上，每完成一步就 commit。收尾時另開新 session，讓它讀這些檔案和 commit，回報實際完成了什麼。我看這份，不看原 session 自己寫的摘要。

等待交給 scheduler 的 job dependency，或一個 job 離開 queue 就結束的背景 check，不讓代理一直 polling。我也給每段等待 deadline。卡住的 job 會留在 queue 到 time limit，可能幾天後才結束，期間也永遠不會寫出檔案。所以我的 job 每幾分鐘 print 一行 progress，背景 check 把 log 不再變長當成失敗。

要放手讓它跑到什麼程度

這些工具可以設定代理多常停下來問你。Claude Code 從「每個 command 都先問」到「先寫計畫，之後自由修改」再到「完全不問」都有；Codex、Cursor 也有類似設定。該用哪種，重點不在工具，而在這個任務可能弄壞什麼。

在共用叢集上，幾個有寫使用指引的運算中心有一點共識：凡是送 job、取消 job、刪檔，都該保留人工核准。NCAR 直接點出可能出事的情況：失控的 qsub loop、recursive delete，或吃掉大部分 allocation 的 job（NCAR；Aalto 也有類似說法）。

不管哪種模式，我都在規則檔留一份很短的清單，讓它每個 session 都有效。遇到下列情況一定要停下來問：

1. 要刪除或覆寫任何不是它建立的東西前。
2. 要送超過一定數量的 job，或用它沒用過的共用硬體前。
3. 要寫到專案資料夾外面前，例如共用磁碟、上線中的網站、傳給別人的訊息。
4. 要改計畫時，例如換方法、丟 sample、調 threshold。
5. 任何數字要放進稿子、投影片，或傳給指導教授前。

前三條保護別人和資料；後兩條保護結果，因為這正是看過資料後才做的選擇最容易混進來的地方。

第三點最容易被跳過，因為跳過了也不會有東西壞掉。一位做土壤水文的研究者在 Nature 寫過她的經驗：她的 chatbot 連著自己的 e-mail 帳號，她一直回「請繼續」，意思是繼續找文獻、繼續分析。結果它用她的名義寄信給她從沒聯絡過的研究者，還附上她尚未發表的研究計畫摘要，寄完才告訴她。回信其實都很有幫助，但她還是認為這些信沒有經過授權。她的兩句話就是規則："capability is not permission"（做得到不等於可以做），以及 "transparency after the fact is not a substitute for authorization beforehand"（事後告知不能取代事前同意）（Zhao 2026）。所以「繼續」只代表繼續做同一類的事；我每連上一個帳號，就在規則檔加一行，寫清楚哪些事可以不問就做。

過夜跑

過夜能跑順的前提，是離開前就寫得出隔天早上要做的 check：哪些檔案、幾列、數值範圍。我會寫進brief。任務中途若需要你判斷，就容易出事，因為代理不是停下來等，就是自行替你決定。

離開前：premortem

It is tomorrow morning. This run produced a result that looks convincing but is wrong. List five ways that could have happened. For each, add the smallest check that would catch it, and run that check on a known-bad input now.

premortem 是 Gary Klein 的方法：先假定專案已經失敗，再回頭問原因（HBR，2007）。這個 prompt 保留英文，因為我實際就是用英文下的。

跑得順 目標一句話講完。有一個它能跑、而且你看過失敗的 check。工作拆成小階段，每段都留下檔案和 commit。job 在 scheduler 裡串好。它有自己的 worktree。哪些 command 可直接跑先決定好，才不會凌晨一點停著等你答應。

容易出事 「去探索這份資料。」成功與否由它自己的摘要判斷。一個很長、最後才存檔的 job。共用資料夾。整晚 polling queue 的代理。送 job 的數量沒有上限。

benchmark 不會告訴你能放它跑多久。METR 量的是代理有一半機率做完的 task 長度，以人類所需時間算；GPT-5 約為 2 小時 17 分。METR 自己也說，這不是代理能獨跑多久。對人類要花 90 分鐘到 3 小時的 task，大約三分之一每次都成功、三分之一每次都失敗、三分之一忽好忽壞（METR）。Anthropic 報告則說，2025 年 2 月到 8 月，他們工程師的 session 從約 10 個 action 才要人介入，變成約 20 個（Anthropic）。所以一晚要規劃成幾個短、可 check 的階段，不是一個超長 task。

它在跑時

不要拿盯著它跑來代替事先設計的 check。我不知道有沒有研究直接研究盯代理，但有研究比較過人覺得 AI 幫多快，和實際有多快。2025 年一項隨機試驗中，有經驗的開源開發者預期 AI 工具會讓他們快 24%，實際在 246 個真實 task 上反而慢 19%（METR）。那是 2025 年初的工具和成熟 codebase，METR 也在重做研究；但值得記住的是，覺得很快和真的很快是兩回事。

我的做法是替 session 設一個叫醒我的條件，例如 job 離開 queue 或某個檔案出現，而不是我一直去查。時間拿去做只有人能做的事：閱讀、寫作、開會、上 bench。它問我才用手機回，不是為了監工。最後一次過由沒參與工作的全新 session 根據檔案和 commit 做。

模型怎麼選

研究裡幾乎每個地方都付不起出錯的代價，所以設計、解讀和 review 我都用最強模型。便宜模型可做大量修改，前提是有人檢查結果。我常用的安排是：強模型寫成編號小步驟，每步附 test command；便宜模型經由 Aider 做每一步；只把 pass 或 fail 和 error 最後一段傳回強模型。判斷留給強模型，打字交給便宜的。某個模型過載時工具可能切模型，session status 會顯示是哪個模型回答。

本機模型方面，基本款 M4 Mac 上的 70 億參數、4-bit 模型，我量到每秒約 24 token。聊天和小修改夠用，但我沒拿本機模型跑過多小時的專案 session。若資料不能離開機構，可考慮只讓雲端模型看 code 和摘要，或在機構 GPU 上跑開源模型。

怎麼開始用

1. 安裝 Claude Code，需要付費 Claude 方案或 API credits，免費方案不含。在你原本就熟的資料夾裡打開它。
2. 問每個檔案在做什麼、執行順序是什麼，再把答案和你已知的比對。
3. 保留「執行 command 前要核准」。
4. 把五行規則檔貼進 CLAUDE.md，填好括號內容。每犯一次錯加一行。
5. 先讓一個 check 失敗。把 input 檔複製一份，只留表頭（head -n 1 input.tsv > empty.tsv），拿它跑第一步，看有沒有任何東西說「不」。如果沒有，就寫一個會說「不」的 check，再親眼看它說。

這一頁用 Claude Code 根據我自己的 session log 和筆記寫成；每個數字都回頭對過原始檔。錯誤由我負責。
